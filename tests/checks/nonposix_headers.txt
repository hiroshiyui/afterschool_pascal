# What the runtime asks of a target that is not POSIX, measured against
# **wasm32-wasi** (ADR-0369, ADR-0382).
#
# It was mingw-w64 until 2026-09-10. ADR-0380 dropped Windows as a target, and
# what this gate asks was never about Windows -- it asks whether the runtime
# still depends only on what each unit is *allowed* to depend on, and it needs
# some non-POSIX toolchain to ask with. WebAssembly is the one this project
# now cares about, so the column is wasi's and the mingw answers are in
# `doc/history.md` with the rest of the Windows measurements.
#
# **The answers here are a toolchain's as well as this source's, and that was
# learned the hard way** under the old column: for one commit the gate ran in
# the container matrix job as well, where Ubuntu 24.04's mingw-w64 reported
# `runtime/pasrt.c` as *compiling* while Debian trixie's reported it blocked
# on `_longjmp`. One row cannot be true of both.
#
# So the toolchain is pinned the way ADR-0189 pins a Unicode version: an
# oracle that changes under you is not one. The `non-posix` CI job is the only
# place it is installed, it is a single Debian image, and it is where
# NONPOSIX_REQUIRE is set. A checkout with a different wasi-libc may
# legitimately disagree with a row below, and what that means is that the
# blocker is that toolchain's and not this runtime's.
#
# **The command carries three flags and every one is load-bearing.**
# `-mllvm -wasm-enable-sjlj` is there because without it wasi-libc's
# `<setjmp.h>` refuses outright -- *"Setjmp/longjmp support requires Exception
# handling support"* -- and `pasrt.c` would be blocked by a header that a
# build flag satisfies, with the real blocker hidden behind it, which is
# exactly the §7 row about one bit per unit. And `-nostdlibinc -isystem
# /usr/include/wasm32-wasi` hides the *host's* headers, which are otherwise on
# clang's search path for this target: a header wasi-libc has not got and
# glibc has would be found and reported present. Every answer below was taken
# both ways and none differed -- glibc's copies fail on their own `bits/`
# internals -- but "it happens not to bite" is not a claim. And
# `-D_WASI_STRICT_PTHREAD` is what makes two wasi-libc sysroots give one
# answer about threads, for the reason `pasrt_task.c`'s row below sets out.
#
# `runtime-isoc` bounds each translation unit by the headers it may include;
# this asks the question that one cannot: **are those headers there on a
# platform that is not POSIX**, and does the unit compile once they are. Every
# target this tree compiles the runtime for is `*-linux-gnu` -- `target-sizes`
# builds it for nine triples and all nine are Linux -- so until this file the
# answer was a measurement somebody took by hand once and wrote into a
# roadmap row.
#
# **The whole point is that a floor becomes a list.** A missing header is a
# *fatal* error, so compiling the unit tells you the first one and nothing
# about the rest: the hand measurement said `pasrt_posix.c` stops at
# `netdb.h` and that "the rest of its 1 177 lines was never reached" -- and
# on this target it stops at `netdb.h` too, five headers being absent. Each
# `#include <...>` is therefore probed on its own, one one-line translation
# unit per header, and what comes back is every header the target lacks.
#
# Two claims, both directions each:
#
#   unit:    <name>  compiles | blocked | crt <MACRO>
#   header:  <name>  <header>        one row per header the target lacks
#
# **`crt` is a third answer because two were hiding one.** A unit that does not
# compile as the toolchain is configured, and does compile once the target's
# modern C runtime is selected, wants no change to this source at all -- it is
# not in the position of one that names a header nobody has. It is checked in
# *both* directions: the unit must fail without the macro and compile with it,
# so the row cannot become a way to excuse a unit that is simply broken.
#
# A unit that stops compiling, one that starts, a header that goes missing and
# a header that arrives are four failures and not one -- the KNOWN_GAP rule
# (ADR-0013) applied to a port. Progress must be recorded here, so closing a
# blocker is a commit that edits this file.
#
# What this cannot see is a unit blocked for a *new* reason while still
# blocked for an old one: the status is one bit. doc/sop.md 7 carries that.

# --- which translation units compile for the target -----------------------
#
# **Two of four compile, and the two that do not are blocked by two different
# kinds of thing** -- a set of headers, and a target capability. Neither is a
# name this source uses wrongly, which is what the column said for one day and
# is corrected below.
#
# `pasrt_unicode.c` compiling clean is the whole of AP 6.4.15 -- normalisation
# and grapheme segmentation over tables, and nothing else. It is the one unit
# a port gets for free, and it is measured here rather than hoped for. It was
# free on mingw-w64 too.
#
# **`pasrt.c` compiles, and the day it spent catalogued `blocked` is the
# finding** (ADR-0383). It was recorded as blocked on `_longjmp` -- and as the
# second non-POSIX target in a row to lack that name, which made the non-local
# goto look like this runtime's one portability question. wasi-libc declares
# both `_setjmp` and `_longjmp`; what hid them is `__STRICT_ANSI__`, the
# header putting them behind `_XOPEN_SOURCE || _GNU_SOURCE || _BSD_SOURCE`,
# and this gate compiled with `-std=c11` while CMake builds every one of these
# units with `-std=gnu11`. So the gate asked a question no build here asks and
# answered it about the runtime. `-D_POSIX_C_SOURCE` alone does not unblock
# it, which is the precise fact underneath: `_longjmp` is XSI and not base
# POSIX. mingw-w64 genuinely had neither name, which is why one measurement
# looked like confirmation of the other.
#
# `pasrt_task.c` is blocked on **threads**, and it took two machines to say
# so. It was catalogued `compiles` for one commit, measured on a checkout
# whose wasi-libc declares `pthread_create` freely; CI's trixie sysroot
# refuses it with a static assertion, and one row cannot be true of both. The
# macro `_WASI_STRICT_PTHREAD` is what makes them agree, and it is the newer
# header's own way of being asked -- *"This function is not available on a
# single-threaded target"*. That is the substance: AP 6.4.16's channels and
# AP 6.9.3.12's tasks want the threads proposal, a target without it cannot
# create a thread, and `-fsyntax-only` on a permissive header would have
# reported the language's concurrency as portable to a platform that cannot
# run it. What a port pays here is the whole task facility, not a header.
#
# `pasrt.c` carried one warning that no exit status did, and it was real:
# `tmpfile` is *deprecated on WASI* -- wasi-libc declares it and does not
# define it -- so the unit compiled and failed at the **link**, at three
# sites, which is `wasm32`'s largest single row until ADR-0388 stopped
# calling it. **The lesson stands with the warning gone**: this gate reads
# exit statuses, a deprecation attribute is not one, and a unit catalogued
# `compiles` can still be a unit nothing can link. And the
# `-mllvm -wasm-enable-sjlj` in the command is what makes `<setjmp.h>` usable
# at all, which is a build flag and not a source change.
unit  pasrt.c            compiles
unit  pasrt_posix.c      blocked
unit  pasrt_task.c       blocked
unit  pasrt_unicode.c    compiles

# --- the headers the target has not got -----------------------------------
#
# `pasrt.c`, `pasrt_task.c` and `pasrt_unicode.c` have every header they name.
# What blocks `pasrt_task.c` is *inside* one of them -- a refusal to declare
# what a single-threaded target cannot do -- which is a different claim and is
# not this file's.
#
# **Five, and the shape of them is the finding.** `pasrt_posix.c` names
# seventeen headers and twelve are here: the directory walk, the file
# information, the file model, and -- unlike mingw-w64 -- `<poll.h>`,
# `<sys/socket.h>` and `<sys/ioctl.h>`, wasi having a socket API of its own.
# What is missing is `<netdb.h>` (name resolution), `<spawn.h>` and
# `<sys/wait.h>` (there are no processes), `<signal.h>` and `<termios.h>`
# (there is no terminal and no signal).
#
# So a port's shape is different from Windows': the sockets are half there and
# the *processes* are not there at all. `PasProcess.Execute` has nothing to be
# implemented over, and `PasNet` would need whatever wasi's own socket
# interface calls resolution. Which of those a first port ships is the open
# question, and a port that ships neither is much smaller than "port
# pasrt_posix.c".
header  pasrt_posix.c  netdb.h
header  pasrt_posix.c  signal.h
header  pasrt_posix.c  spawn.h
header  pasrt_posix.c  sys/wait.h
header  pasrt_posix.c  termios.h
